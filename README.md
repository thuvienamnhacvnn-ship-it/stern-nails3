# Stern Nails 3

The studio's website and booking system: catalogue, lookbook, appointments,
gift cards, customer accounts, a look assistant, and an admin calendar. German
by default, English throughout. Built from the design kit in
`Stern-Nails-3-Sage-KIT`.

**This build runs in demo mode.** Every price, member of staff and appointment
in it is example data, no mail leaves the machine, and no money can move. What
still has to happen before it is a live website is in
[HANDOVER.md](HANDOVER.md).

---

## Running it

Node 20 or newer, and ffmpeg on the PATH if you want to rebuild the images.

```bash
npm install
npm run db:migrate     # create the tables
npm run db:seed        # demo catalogue, looks and staff
npm run dev            # http://localhost:3110
```

Then:

- the site — <http://localhost:3110/de/start>
- the admin — <http://localhost:3110/admin/login>,
  `admin@stern-nails.demo` / `stern-demo-2026`
- mail that would have been sent — `.data/outbox/`, and the admin outbox at
  **Einstellungen**

Copy `.env.example` to `.env.local` if you want to change anything. Every
default in it is the inert one.

### One process at a time

The database is [PGlite](https://pglite.dev) — Postgres compiled to WebAssembly,
running inside the Node process against `.data/pg`. A native Postgres cannot be
installed on the workstation this was built on, and PGlite speaks the same SQL,
so moving to a server later is a connection string rather than a rewrite.

It allows exactly one process to hold the data directory. **Stop `npm run dev`
before running a migration, a seed or the tests** — the scripts check the dev
port and refuse rather than corrupting the database, but it is easier to just
stop the server.

## How it is put together

```
assets/            the design kit's originals — the only images that are edited
public/media/      what the browser downloads, generated by `npm run assets`
public/fonts/      self-hosted woff2; no request ever goes to Google
src/db/            schema and the PGlite handle
src/lib/           the rules: time, money, availability, booking, payments,
                   vouchers, auth, the stylist
src/components/    the interface
src/app/[locale]/  the customer site, one route per translated segment
src/app/admin/     the studio's own pages, separate session and layout
src/app/api/       JSON endpoints and webhooks
scripts/           asset pipeline, migrations, seed, tests, screenshots
drizzle/           generated SQL migrations
```

Next.js 16 with the app router, React 19, Drizzle over PGlite, Zod at every
boundary, and hand-written CSS with design tokens. No UI library, no CSS
framework, no icon package — the design is specific enough that each of those
would have cost more than it saved.

### Light and dark

One design, two palettes. The default follows the visitor's system; a three-way
switch in the header — light, dark, match my device — overrides it and is
remembered per browser.

Three things make it work rather than half-work:

- **Every colour is a token.** There is no hex typed into a component, because a
  hex is a thing that will not follow the theme. `npm run shots` captures both
  palettes on every page for exactly that reason.
- **Photographs are never touched.** No overlay, no filter, no dimming. The nail
  sets and the studio's own photographs are the product.
- **The wordmark has two inks.** "stern NAILS 3" is moulded in dark olive and
  would be a hole on a dark page, so the asset build generates a cream version
  and CSS picks one. The flower needs no variant. A handful of surfaces that are
  a colour in their own right — the gift card, a caption over a photograph —
  keep their own ink in both themes.

A small inline script applies a remembered theme before the first paint.
Without it, someone who chose dark gets a white flash on every navigation.

### Images

`npm run assets` turns the kit's originals into what the browser downloads:
AVIF and WebP at the widths the layout actually asks for, plus a JPEG fallback,
with intrinsic sizes recorded in `public/media/manifest.json` so nothing
reflows while loading. Sources are never upscaled.

It also lifts the flower and the `stern NAILS 3` wordmark off the cream card
they were delivered on, with real transparency, so the header can set them side
by side the way the design screens do. That is done with ffmpeg and a small
alpha computation rather than sharp, because this workstation blocks unsigned
native node bindings.

Every URL under `/media/` is served `immutable`, and the filenames only carry a
width — so a rebuilt picture at the same size would never reach a browser that
had seen the old one. The manifest therefore records a hash of each source and
every URL carries it as `?v=`. Change a file in `assets/`, re-run
`npm run assets`, and the URL changes with it. Nothing else has to be touched.

`assets/interiors/hero-banner.png` is the start page, and it is used exactly as
delivered: the brand sign, the written line and the card on the table are all
painted into the photograph, so the page does not draw them a second time. It
is 16:9 and it is shown whole: the banner is one screen, and the picture is
fitted into it (`object-fit: contain`) rather than made to fill it. A window is
wider than 16:9, so filling it would mean cutting the top and the bottom off the
frame — and the bottom is where the written line, the card on the table and the
flowers are. What is left at the sides is the banner's own dark, which the
picture's near-black foliage edges run straight into, and which the headline and
the lookbook rail sit on. On a phone the picture is a header strip instead and
is cropped to the model.

### Time

Everything stored is a UTC instant. Everything displayed is Europe/Berlin wall
time. The two are not a fixed offset apart, so the conversion goes through the
platform's own tz database (`src/lib/time.ts`) and the tests pin both sides of
the spring and autumn changeovers.

### Money

Integer cents, everywhere. A service the studio has not priced is `null`, not
zero — it renders as "Preis auf Anfrage", it cannot be paid for online, and a
`null` anywhere in a basket makes the whole total `null` rather than the sum of
the rest.

### Booking

```
draft ──hold──▶ held ──▶ pending_payment ──▶ confirmed ──▶ completed
  │               │             │                │
  └───────────────┴─────────────┴────────────────┴──▶ cancelled
                                                  └──▶ no_show
```

Two rules matter more than the diagram:

- **Prices come from the database, in this process, every time.** The browser
  sends slugs and a booking id. It never sends a total, and a total in a request
  would be ignored.
- **Passing the availability view is not a reservation.** The confirming
  transaction re-checks for conflicts against everything except the booking's
  own hold. Two customers racing for 14:00 both get past the calendar; only one
  gets past that check, and the other keeps their form and their hold.

### Payments

Behind one adapter. `demo` is a fake that creates intents and signs its own
webhooks; `stripe` and `paypal` are named so the shape is visible and throw,
because an unconfigured integration must fail rather than quietly succeed.

A return URL proves nothing — only a signed webhook marks a payment `paid`, and
that same path runs in demo mode, so duplicate delivery, out-of-order events and
a payment that settles after the hold expired are all exercised by every demo
booking rather than discovered on the first live one.

### The stylist

It recommends at most three looks, by slug, from the published lookbook; slugs
it invents are dropped. It reads — it cannot book, cannot hold a slot and cannot
claim a time is free. It refuses anything that reads as a medical question and
points at a doctor instead. No customer email, phone number or appointment ever
goes into a prompt.

With no key configured it runs a rules recommender over the same catalogue, and
that is what the demo uses. That path is not a degraded mode to apologise for —
it is the offline behaviour the error states promise.

## Testing

```bash
npm test
```

46 assertions against a throwaway database in `.data/test`, covering what the
brief asks for: the clock change, an expired hold, a price that moved between
booking and confirming, a double submit, a failed payment, a duplicate webhook,
a late webhook, overspending a gift card, one customer reaching another's
booking, and a member of staff reaching the owner's settings.

One caveat stated plainly: PGlite runs everything through a single connection
and serialises transactions, so two `await`s in a `Promise.all` are a queue, not
a race. The suite therefore asserts the *mechanisms* that make those races safe
— the conflict check inside the confirming transaction, and the conditional
`UPDATE` that guards a gift-card balance — rather than pretending to reproduce
concurrency the engine cannot produce. On a Postgres server those same
mechanisms are what hold.

Layout was checked at 390, 768, 960, 1280, 1440 and 1920 CSS pixels in both
languages: no page scrolls sideways, and the one-screen desktop layout gives up
and scrolls normally below 1100×780, which is also what happens at 200% zoom.

Contrast was measured rather than judged, by walking the rendered DOM in both
themes and comparing every piece of text against its computed background. Body
text sits around 13:1 and secondary text around 7:1. The only things below 4.5:1
are calendar days that cannot be booked, which are disabled controls and exempt,
and which still read at about 3:1.

## What is not built

Named rather than hidden:

- **The admin week view.** The day view is complete; the week toggle would be a
  dead tab, so it is absent.
- **Editing look and service text in the admin.** Publication, price and
  duration are editable. The two-language copy needs a content editor the studio
  has not asked for.
- **Rescheduling in place.** Cancelling and rebooking works; a true
  drag-to-move on the calendar does not exist.
- **Real payment providers, real mail, WhatsApp.** See `HANDOVER.md`.
